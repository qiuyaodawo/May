# 配置并检查团队验收

[English](../../en/guides/maybecode-team-verification.md) | **简体中文**

通过结构化报告和宿主定义的检查，可以判定团队任务是否满足要求。执行状态和
验收状态分别保存，任务已经 `completed` 时，验收仍然可能是 `unverified`。

本指南要求已有[团队计划](maybecode-team-plan.md)，每个任务副本中已经提供检查
需要的依赖。启动前定义所需检查；命令检查需要创建团队时提供 `--allow-checks`，
授权前应审查可执行文件、参数和实际执行的代码。

## 验证团队

1. 在计划中增加任务对应的检查，并为相应角色提供 `submit_report` 和 `run_check`。
2. 使用 `--plan <path>` 启动团队。存在命令检查时增加 `--allow-checks`。
   在仓库执行时添加 `pnpm` 前缀。
3. 执行结束后，通过 `maybecode team verify <id>` 运行配置检查，针对当前
   工作区内容重新计算验收状态。
4. 使用 `maybecode team status <id>` 检查各项报告和检查记录。
   通过验收需要当前报告和该任务的全部检查通过。检查状态为 `unknown` 时，
   根据[团队恢复](maybecode-team-recovery.md)核查结果，随后才可以再次检查。

## 结构化报告

`submit_report` 工具保存摘要和数量受限的问题发现或修改建议。以下参数展示
读取实际 `average.mjs` 对应行之后提交的报告格式，路径、行号和引用需要根据
已经检查的文件填写：

```json
{
  "summary": "平均值实现的分母有误。",
  "claims": [
    {
      "kind": "finding",
      "text": "除数多计了一个元素。",
      "evidence": [{ "path": "average.mjs", "startLine": 4, "endLine": 4, "quote": "values.length + 1" }]
    }
  ]
}
```

宿主固定任务、dispatch 和 turn 身份，检查相对路径、文件是否存在、行号范围和可选引用文本，并记录文件哈希。这些检查只能证明引用的字节存在，**不能**证明结论逻辑正确或完整。报告不可变，工具调用身份幂等，后续报告保留之前的历史。

单份报告最多 64 KiB、64 条结论，每条结论最多 16 处证据。拒绝绝对路径、路径穿越、符号链接和未知字段。引用匹配时将 CRLF 统一为 LF。

## 宿主定义的检查

在[团队计划](maybecode-team-plan.md)的 `checks` 字段定义检查。检查 ID 全局唯一，并且属于一个已声明的任务：

```json
[
  { "id": "divisor", "taskId": "implementation", "type": "file-contains", "path": "average.mjs", "text": "total / values.length" },
  { "id": "tests", "taskId": "implementation", "type": "command", "command": "node", "args": ["--test", "average.test.mjs"], "timeoutMs": 30000, "maxOutputBytes": 65536 }
]
```

此片段是 `checks` 字段的内容。完整计划还需声明 `implementation` 任务，
任务副本中提供 `average.mjs` 和 `average.test.mjs`，宿主 PATH 中提供原生
`node` 可执行文件。根据项目调整这些内容。副本复制排除的依赖目录需要另外准备。

支持的检查类型：

- `file-contains`：精确的 UTF-8 子串匹配。
- `file-sha256`：精确文件 SHA-256，配置为 64 位小写十六进制字符串。
- `command`：宿主配置的精确可执行文件与参数列表。退出码为零只表示该检查通过，不能证明测试本身有意义。

模型调用 `run_check` 时只能传 ID，不能替换命令、参数、超时、输出上限或工作目录。命令检查还需要显式 `--allow-checks` 授权。即使团队为只读模式也一样：只读文件工具不能约束已授权进程的行为。

命令不经过 shell，固定在任务工作副本中运行，仅继承少量环境变量，不继承 API 密钥、`NODE_OPTIONS` 等；Windows 进程隐藏窗口，输出和时间有界。默认 30 秒和 64 KiB，上限 120 秒和 1 MiB。

Windows 上使用 `node.exe` 等原生可执行文件，传入包管理器的 JavaScript
入口和参数数组，`.cmd` 和 `.bat` 无法直接执行。进程启动失败时记录 `failed`，
已启动但结果未知的进程需要核查恢复。

测试进程具有宿主权限，可以读取工作区之外的文件、获取其他文件中的凭据、
访问网络、写入副本之外的目录或启动子进程。结束直接子进程后仍需确认后代进程
已经停止。仅授权经过审查的命令，不可信代码使用外部沙箱。凭据保存在参数和
可继承环境变量之外，输出和报告作为本地私有任务数据保存。

## 新鲜度与验收

报告和每次检查都绑定任务副本中**全部**文件路径、目录名和文件内容的指纹。检查上限为 10,000 个条目和 64 MiB，并拒绝符号链接。检查运行前后分别记录指纹。如果运行期间或之后工作区发生变化，结果就会过期，不能授予验收通过。测试生成的新文件也会使原指纹失效，不会默默忽略变更。

只有存在当前结构化报告，并且该任务的全部配置检查都对这些确切字节通过，验收才是 `passed`。当前报告的无效证据或失败检查得到 `failed`。未配置检查、缺少结果、结果过期、执行中断或缺少当前报告得到 `unverified`。重试必须使用当前 dispatch 和 turn，不能沿用旧报告。验收只覆盖配置的检查，不代表程序总体正确。

用 `team verify <id>` 显式发起宿主验证，用 `team status <id>` 分别查看执行状态与验收状态。任务完成时可以计算文件断言；状态查看、恢复和验收读取不会偷偷重新启动命令检查。

静态下游任务会随依赖答案收到有界的宿主验证记录。它说明检查针对的是该依赖
任务的私有副本。同伴文本仍是不可信数据，
宿主记录也不会证明其全部自然语言结论正确。

## 检查中断

本地单写者日志在检查启动**之前**先写入并 fsync `pending` 意图。超时、取消、输出超限、不确定终止或恢复时发现 pending，都会得到 `unknown`。相同命令身份绝不会启动另一个进程；pending/unknown 检查会阻止该任务的后续检查。

恢复前应检查外部影响并终止残留进程。宿主核查操作记录证据，只能将 `unknown`
检查标记为 `failed` 或 `cancelled`，不执行检查命令。后续授权的验证需要新的
命令身份。崩溃遗留的写锁需要宿主核查，不会自动接管。验证日志已经记录成功时，
另一份中断的 Session 工具检查点仍需单独核查。

存储在 `verification.jsonl` 中保留报告和全部检查命令身份：日志上限 16 MiB，最多 256 份报告、512 次检查。只读状态检查不获取写锁。读取时忽略不完整的最后一行，后续独占写者会修复该尾行；已经提交但格式错误的记录会被拒绝。

512 次检查配额按照不同命令身份计算。达到配额后拒绝新检查，已有状态仍可读取。
